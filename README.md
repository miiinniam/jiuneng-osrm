# OSRM++ 项目结构导航

这个项目里"正算公式"（给一条运输需求算报价）、"反算/校准"（从真实成交价倒推市场费率）、
"车辆型号库"（车辆的载重/尺寸/费率等主数据）是三个不同的关注点，分别放在不同位置。
下面这份地图帮你快速定位改动应该动哪里；每个方向的具体细节、改动清单，
去对应目录里的 SKILL 文档看。

## 正算公式（forward）—— 实时给一条报价算多少钱

**代码位置**：`backend/app/services/费用计算公式.py`（唯一公式实现，纯函数/常量）+
`backend/app/services/cost_engine.py`（编排：查车型、拼货自动匹配、组装结果）。

这两个文件是 FastAPI 应用真正在跑的代码，必须留在 `backend/app/` 的 Python 包结构里
才能被正常导入，**不能挪到别的顶层目录**，这是 Python 项目结构的硬性要求，不是可以
自由调整的文档摆放问题。改公式只改 `费用计算公式.py` 一个文件，工程性代码
（查表、异常处理、结果组装）留在 `cost_engine.py`。

## 反算/校准（reverse）—— 从真实报价反推市场费率

**代码位置**：`backend/app/services/calibration.py`（同样是应用代码，留在包结构里）。

**技能文档+数据**：全部放在 `公式反算文件/` 目录——这个目录只放"反算专属"的东西：

- [`报价数据提取SKILL.md`](./公式反算文件/报价数据提取SKILL.md)：第一阶段，把任意
  格式的原始供应商报价（Excel/Word/PDF）整理成标准样本 JSON。
- [`运费反算SKILL.md`](./公式反算文件/运费反算SKILL.md)：第二阶段，用样本 JSON 跑
  最小二乘拟合，反推 `R_base`/`R_wage`/`P_fuel`。
- `供应商报价/`：原始报价文件 + 提取出来的样本 JSON + 地理编码缓存。

## 车辆型号库（正算/反算共用）—— 不属于"反算专属"，单独成目录

**位置**：`车辆型号库/` 目录：

- `车辆型号库.csv`：车型主数据（5大类、具体型号的载重/容积/费率/油耗等），用户直接
  用 Excel 维护，后端启动时一次性加载（`backend/app/services/vehicle_registry.py`
  读取这份 CSV，改了内容要重启后端才生效，不做热重载）。
- [`车辆型号库变更指南SKILL.md`](./车辆型号库/车辆型号库变更指南SKILL.md)：**这份
  数据/代码结构本身要改动时**（新增字段、新增大类、改匹配逻辑……）的完整关联关系图和
  操作清单——车型库被正算/反算/前端/测试到处引用，改结构容易漏改地方，照着这份文档走。

这份数据之所以没有放进 `公式反算文件/`，是因为它不是反算专属的东西——每一次正算报价
请求都要读它，只是恰好也被反算流程用来把历史样本的 `model_id` 换算成载重/容积。

## `skills/` 目录

`skills/运费反向测算/`、`skills/车辆型号库变更指南/` 下面都是给 Claude Code 这类
agent 用的短指针文件，实际内容都在上面列的实际工作目录里，避免同一份内容两处维护、
越改越不一致。

## 一键启动（Docker Desktop）

推荐方式：**全部通过 Docker Desktop 启动**（OSRM 引擎 + 后端 API + 前端），不需要 WSL2。

```bash
cd OSRM++
docker compose up -d
```

| 服务 | 端口 | 地址 |
|------|------|------|
| OSRM 路由引擎 | 5001/9966 | http://localhost:9966 |
| 后端 FastAPI | 8000 | http://localhost:8000/docs |
| 前端 Next.js | 47820 | http://localhost:47820 |

也可使用 `一键启动.ps1`（保留作为备用，OSRM 在 WSL2 Docker，后端/前端在 Docker Desktop/原生）。
