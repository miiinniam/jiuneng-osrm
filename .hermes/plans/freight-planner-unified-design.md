# 玖能「货运一站式」系统设计 — OSRM++ 报价 × Carbox 3D 装载 糅合方案

> 版本: v1.0 · 2026-08-19 · 负责人: @codex-01
> 目标: 一套以客户使用流程为主线、AI 自然语言为入口、可通用的货运规划系统

---

## 0. 一句话

把「报价」和「装载」从两个孤岛，变成一条**客户流程**：客户用自然语言描述货物 → AI 解析成结构化清单 → 自动算「装几车、怎么装、多少钱」→ 输出可交付的方案（装车图 + 装箱单 + 报价单），全程可用对话追问和修改。

---

## 1. 现状差距（为什么必须糅合）

| 维度 | OSRM++（报价） | Carbox（装载） | 糅合后 |
|---|---|---|---|
| 输入 | 表单：重量/体积/车型/路线 | 表单：货物明细/车型 | **自然语言**："3托盘120×80 + 200箱60×40，从凭祥到河内" |
| 输出 | 运费明细 | 装车方案/装载率 | **完整方案**：装几车+怎么装+多少钱 |
| 数据 | 31 车型库、边关费、汇率 | 9 车型、确定性 AABB 内核 | 同一份货物清单贯穿两引擎 |
| AI | 已有聊天 + 6 工具 | 无 | 双引擎统一对话操控 |

**核心洞察**：`CargoInput.items`（单件明细，OSRM++ 已有 schema）和 Carbox 的 `cargo`（货物清单）**是同一份数据的两种表达**。糅合的本质 = 让货物清单在「自然语言 → 结构化 → 装载计算 → 费用计算」链路中单向流动，不再重复录入。

---

## 2. 客户使用流程（主线设计）

### 场景 A：快速方案（默认入口）——「我说货，系统给方案」

```
用户: "我有 3 个托盘（120×80×120cm, 每个800kg）和 200 箱（60×40×40cm, 25kg/箱），
      从友谊关运到河内，帮我看看怎么装、要多少钱"
                    │
                    ▼
┌─ AI 解析层 (LLM + 结构化输出) ─────────────┐
│  ① 提取货物清单 → 匹配 31 车型库候选车型     │
│  ② 调用装载引擎 → 各车型自动装载 → 装载率/车数 │
│  ③ 调用报价引擎 → 路线距离 + 运费明细          │
└──────────────────────────────────────────┘
                    │
                    ▼
┌─ 方案卡片（AI 生成，可追问）─────────────────┐
│  📦 40HQ：装 1 车，利用率 78%，总重 8.6t     │
│     ↓ 展开：3D 装车图（Carbox 渲染）          │
│  💰 运费：¥8,420（明细：油费/工资/边关费…）   │
│  [换车型] [改货物] [导出方案] [下订单]        │
└──────────────────────────────────────────┘
```

### 场景 B：装载规划优先——「先看怎么装，再谈钱」

```
用户: "这些货 40HQ 装得下吗？"
  → 装载引擎 + 3D 视图（现有 Carbox 全部交互：拖拽/推挤/旋转/统计）
  → 装不下时 AI 建议: "装不下 120 箱,可换 17.5m 平板或分 2 车"
用户: "换 17.5 平板试试" → 一键切换车型重算
```

### 场景 C：报价优先——「先问价，再配车」

```
用户: "从河内到胡志明整车 13m 平板多少钱？"
  → 报价引擎直接答（现有 AI 工具 calculate_freight_cost）
  → 追问 "如果我只有 6 吨货呢" → 拼车/整车模式切换
```

### 场景 D：批量方案（客户经理场景）

```
用户: "帮我批量算这 20 行货的装载和报价"
  → 现有 /batch 批量报价 + 装载率列新增 → 导出 Excel
```

**三态归一**：A/B/C 只是入口不同，共享同一「货物清单 → 装载 → 报价」核心链路。D 是 A 的批量版。

## 3. 系统架构（糅合设计）

```
┌─────────────────────────────────────────────────────┐
│ 前端 Next.js (官网 + 工具)                            │
│  /               首页（含「货运方案」主入口）            │
│  /planner        糅合工作台 ← 新增，三态场景合一        │
│  /tools/loader   Carbox 3D（一期 iframe, 二期原生）    │
│  /quote /batch   现有报价/批量（保留）                  │
└──────────┬──────────────────────────────────────────┘
           │ REST / SSE
┌──────────▼──────────────────────────────────────────┐
│ 后端 FastAPI                                          │
│  /ai/chat         现有聊天 + 工具（升级）               │
│  /planner/parse   自然语言 → 货物清单 (LLM 结构化)      │
│  /planner/plan    货物清单 → 装载方案 (调 Carbox 内核)  │
│  /planner/quote   货物清单 + 车型 → 报价 (调 cost_engine)│
│  /tools/loader-api 包装 Carbox 确定性内核 (二期原生用)   │
└──────────┬──────────────────────────────────────────┘
           │ 内部调用
┌──────────▼──────────────────────────────────────────┐
│ 引擎层                                                │
│  cost_engine.py  (报价: 31车型/边关费/汇率/OSRM路由)    │
│  packer 内核      (装载: 确定性 AABB, 4策略/推挤/沉降)  │
└──────────────────────────────────────────────────────┘
```

### 关键设计决策

1. **Carbox 内核 Python 化（二期核心）**：`packer.js` 是纯确定性 AABB 算法（~287 行，无 DOM/Three 依赖），可 1:1 移植成 `packer.py` 供后端调用——同一算法、同一结果（回归守住 40HQ 75.7% 基线），前端 3D 只做渲染。这是「AI 自然语言操控装载」的技术前提：AI 要能调装载计算，就必须有服务端可调的内核。
2. **一期先用 Node 桥**（可选）：若 Python 移植未排期，`/planner/plan` 可用子进程调 `node packer.js`（纯 JS 无依赖，已有 headless 验证脚本可复用）——零移植成本先打通链路，二期换 Python。
3. **货物清单是唯一真相**：`CargoItemInput`（OSRM++ 已有）作为 canonical schema，Carbox 货物是它的渲染/装载投影。录入一次，两引擎共享。
4. **AI 工具扩展（双引擎对话）**：
   - `plan_loading(cargo_items, vehicle_ids)` → 装载方案（新增，调 packer）
   - `calculate_freight_cost`（已有）→ 报价
   - `suggest_vehicles(cargo_items)` → 车型推荐（新增：遍历 31 车型装载率排序）
   - 现有 `_query_vehicles/_compare_routes/_geocode/_query_exchange_rate` 保留
   - **实现约束（@codex-03 审查补充）**：新增工具必须三处同步——`ai_tools.py` 的 TOOLS schema + `execute_tool()` 分支 + `ai_chat_prompt.py` 系统提示。少一处 AI 就调不到或报未知工具。
5. **通用性**：系统不绑定玖能品牌——车型库、边关费、汇率、模板、税率都是配置（现有 backend/data + presets 已是配置化），新增「货物清单模板库」（常用货：托盘/纸箱/桶/设备等，从 Carbox QUICK_SIZES 提炼）+ 方案导出模板。可服务任何货运客户。
6. **31 车型 → 内核映射口径（@codex-02 补充）**：调内核 `setCustomTruck` 时，**H 必须用 `max_cargo_height_m` 而非外尺寸 `height_m`**，`maxWeight = max_load_ton × 1000`。这决定 suggest_vehicles 排序准确性。
7. **内核缺口：不可堆叠约束（@codex-02 补充 + @codex-03 审查扩展）**：OSRM++ `CargoItemInput.stackable` 已有字段，但 Carbox 内核物理模型没有——现 AI 方案可能把易碎/不可堆叠品压箱底。**三期内核必须加 `stackable=false → 只能落地板` 约束**（贪心 shelf 算法加一个约束）。**注意（@codex-03）：手动拖拽路径也要联动**——`stackHeight`/`supportHeight` 吸附、3D 拖拽两处同改，否则 AI 方案不压易碎品、用户手动拖上去照样压。三期 = 内核 + 拖拽吸附两处一起改，否则「通用性」不成立。
8. **adapter 扩展：AI→3D 闭环（@codex-02 补充 + @codex-03 审查修正）**：二期方案卡「展开 3D 装车图」需把 AI 算好的 placements 喂给 Carbox 渲染。**双路径契约（@web-design-01 落进交互设计 §2.3）**：
   - **读模式**（方案卡小视口）：原始写入 `Planner.placements` + `fire('placement')`，**跳过** centeredPlacement/推挤/沉降一切变换 → AI 方案卡布局 = 3D 渲染布局逐件一致（守验收标准 2）。⚠️ 不能用 `addPlacement()`——它内部会跑变换改坐标。
   - **写模式**（完整工作台）：走正常交互变换，合法。
   - **回写闭环**：工作台改完回对话，最终坐标回写方案卡刷新 → 用户看到/导出/下单的都是真实落位。
9. **/planner 交互设计（@web-design-01 补充）**：整页滚动对话流 + 底部固定输入栏 + 乐观 UI + 打字机流式（对齐已确认的 ChatGPT 网页版式）；方案卡 = 结构化工件（装载方案 + 3D 展开区 + 费用明细三区块，动作 [换车型/改货物/导出/下订单]）；3D 两级展开（卡片内只读小视口 → 「打开完整工作台」新 tab 进可编辑态）；追问即新对话轮，卡片原位刷新但上一条可回看；货物清单常驻 chip 条全局可见可改。详见 `loader-design/planner-interaction-design.md`。

## 4. 客户价值（实际应用场景）

| 用户角色 | 现在 | 糅合后 |
|---|---|---|
| 发货客户 | 打电话/微信问价，Excel 对装载 | 说人话 → 方案卡（装法+价格）→ 导出装车单 |
| 货代操作 | 报价单 + 装箱单两张表手工拼 | 一个方案卡出两张表，可改可追问 |
| 玖能销售 | 背车型参数 | AI 自动推荐车型+装载率，答得快答得准 |
| 车队调度 | — | 装载方案直接给司机/装卸队（3D 图 + 装箱单） |

## 5. 分阶段落地

| 阶段 | 内容 | 依赖 |
|---|---|---|
| 一期（已在做） | iframe 整合 + 双卡入口 + 互跳参数 | 无 |

## 6. 验收标准

1. 一句话需求 → 方案卡（车型/装载率/车数/运费）正确，与手算一致
2. 装载结果与 Carbox 独立版逐件坐标一致（Python/Node 内核回归）
3. AI 追问闭环："换车型/加货/改目的地"都能改方案
4. 导出：装箱单（CSV）+ 报价单（现有模板）
5. 回归：40HQ 600 件 ≈75.7% 基线（**货物规格钉死：600 件 60×40×40cm ×25kg**，装 40HQ 1203×235×269；40³×600 只有 50.5% 属规格不符）、推挤 9 场景不破
