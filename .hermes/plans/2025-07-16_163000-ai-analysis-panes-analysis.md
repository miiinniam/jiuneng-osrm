# AI 分析窗格 — 功能定位与架构分析

> 副标题：为什么不做一个"小号聊天窗口"，而是设计一个真正的分析工具

---

## 一、核心问题：分析窗格 vs 主对话，本质区别是什么？

我原来的第一版计划把它做成了"副聊天窗口"——一个缩小的 Hermes 对话，换了个更快更便宜的模型。但这完全错了。

主对话是 **Agent**，分析窗格应该是 **Analyzer**。两者的区别：

| 维度 | 主对话 (Agent) | 分析窗格 (Analyzer) |
|------|---------------|---------------------|
| **目的** | 执行任务、操作文件、运行命令 | 纯思考、解读、比较、提炼 |
| **工具体系** | 完整工具链（terminal/file/browser/delegate） | 零工具，只有推理 |
| **上下文** | 长对话、多轮迭代、项目全貌 | 短上下文、聚焦单次分析 |
| **状态** | 有状态（session、memory、plan） | 准无状态（最多保留最近 3-5 轮） |
| **模型** | deepseek-v4-pro（强推理，贵） | deepseek-chat / v4-flash（快，便宜） |
| **交互** | 持续对话，来回修正 | 一次输入 → 获得分析 → 可能追问 |
| **定位** | "帮我做" | "帮我看/帮我想" |

**关键洞察**：你在主对话里让 Agent 分析一段代码，它会消耗主对话的 token 预算、污染上下文、可能触发不必要的工具调用、响应慢（pro 模型推理深）。而分析窗格是**旁路通道** ——不走 agent loop，不提工具，不记 memory，不写文件。

## 二、真实使用场景分析

结合你的工作环境（OSRM++、ASD 系统、越南物流、翻译器），分析窗格的实际使用场景：

### 场景 1：代码片段快速审查
```
主对话正忙于跑 OSRM++ 的路由测试 →
你看到一段可疑的路径计算逻辑 →
粘贴到分析窗格："这段代码有什么潜在 bug？"
→ flash 模型 2 秒返回分析，不中断主对话
```

### 场景 2：多角度并行分析
```
一个复杂的 SQL 查询 →
窗格 1：语法和性能分析
窗格 2：安全检查（注入风险）
窗格 3：业务逻辑验证
→ 三个角度并行，每个用不同的系统提示词
```

### 场景 3：翻译/术语对照（你有翻译器项目）
```
一段越南语合同文本 →
窗格：翻译 + 风险点标注 + 术语解释
→ 不经过翻译器的 DeepSeek 调用（对比用）
```

### 场景 4：日志/错误分析
```
ASD 系统报错日志 →
粘贴到分析窗格："这个错误是什么原因？给出修复建议"
→ 快速诊断，不需要开新对话
```

### 场景 5：文档速读
```
供应商发来的 3 页报价单 →
粘贴到分析窗格："提取关键信息：价格、条款、有效期"
→ 几秒出结构化摘要
```

**共同特征**：
- 输入是**一段内容**（代码/日志/文档/文本）
- 期望输出是**分析/解读/转换**（不是执行）
- 需要**快**（2-5 秒出结果，不是 10-30 秒）
- **不想**被记入主对话上下文

## 三、重新定义的产品形态

### 3.1 不是聊天窗口，是"分析工作台"

```
┌─────────────────────────────────────────────────────────┐
│  AI Analysis Workbench                                   │
│                                                          │
│  ┌─────────────────┐  ┌─────────────────┐               │
│  │ 📋 输入区        │  │ 🧠 分析结果区    │               │
│  │                  │  │                  │               │
│  │ (paste/send      │  │ (streaming        │               │
│  │  content here)   │  │  analysis)       │               │
│  │                  │  │                  │               │
│  │                  │  │                  │               │
│  ├─────────────────┤  ├─────────────────┤               │
│  │ 🏷 分析模式:     │  │ 📎 动作:         │               │
│  │ [代码审查] [翻译] │  │ [复制] [发送到对话]│               │
│  │ [安全审计] [总结] │  │ [追问] [保存]     │               │
│  │ [解释] [比较]    │  │                  │               │
│  └─────────────────┘  └─────────────────┘               │
│                                                          │
│  ┌─────────────────────────────────────────────────┐    │
│  │ 追问区（可选，保留最近 3 轮对话）                    │    │
│  └─────────────────────────────────────────────────┘    │
└─────────────────────────────────────────────────────────┘
```

### 3.2 核心交互模式：模板驱动，而非对话驱动

用户不是"找分析窗格聊天"，而是：

1. **粘贴内容** （代码/文本/日志/文档）
2. **选择分析模式** （或让 AI 自动推荐）
3. **获得结构化输出** （不是闲聊，是分析报告）
4. **可选追问** （最多 3 轮）
5. **结果导出** （复制/发送到主对话）

## 四、系统提示词架构

### 4.1 基础层 — 通用分析提示词（所有窗格共享）

```
你是一个专业的AI分析助手，运行在独立分析窗口中。
你与用户的"主对话Agent"分离 —— 你不需要执行任何操作，
你只需要分析、解读、思考。

## 核心原则
1. **简洁直接** — 用最短的篇幅给出最精准的分析
2. **结构清晰** — 使用标题、列表、代码块组织输出
3. **证据驱动** — 引用原文中的具体内容，不要泛泛而谈
4. **主动发现问题** — 不仅回答用户问的，还要指出用户没问但重要的点
5. **中文回复** — 除非输入是英文代码/术语，否则用中文

## 输出格式
- 先给结论（一句话总结）
- 再给详细分析（按要点组织）
- 最后给建议/下一步（如果适用）

## 绝对不能做的事
- 不要执行命令或建议用户执行命令
- 不要假装自己有工具（你没有）
- 不要写完整代码实现（除非用户明确要求）
- 不要超过 1000 字（除非内容本身要求）
```

### 4.2 角色层 — 可切换的分析模式（系统提示词叠加）

```yaml
modes:
  code-review:
    label: "🔍 代码审查"
    prompt_append: |
      ## 代码审查模式
      你是资深代码审查专家。对用户提供的代码：
      1. **逻辑错误** — 有没有边界条件遗漏、空值风险、类型错误
      2. **性能问题** — 循环嵌套、不必要的拷贝、N+1 查询
      3. **安全隐患** — 注入风险、敏感信息泄露、权限问题
      4. **可读性** — 命名、结构、注释是否合理
      5. **最佳实践** — 是否符合该语言/框架的惯用写法
      
      输出格式：
      - 🚨 严重问题（必须修复）
      - ⚠️ 建议改进
      - 💡 小建议

  security-audit:
    label: "🛡 安全审计"
    prompt_append: |
      ## 安全审计模式
      你专注于安全漏洞检测。对提供的代码/配置：
      1. OWASP Top 10 风险检查
      2. 输入验证与注入防护
      3. 认证与授权逻辑
      4. 敏感数据处理
      5. 依赖安全（如果有 package.json/requirements.txt）

  explain:
    label: "📖 逐行解释"
    prompt_append: |
      ## 代码解释模式
      像老师一样解释代码。逐段、逐行说明：
      - 这段代码做什么
      - 为什么这样写
      - 有哪些关键概念需要注意
      用通俗语言，假设读者有一定基础但不熟悉这个具体代码库。

  translate:
    label: "🌐 翻译分析"
    prompt_append: |
      ## 翻译与分析模式
      对提供的文本：
      1. 翻译成目标语言（默认中→越或越→中，自动检测）
      2. 标注专业术语（物流/工程/法律）
      3. 指出文化差异需要注意的地方
      4. 如果有歧义，列出多种可能的理解

  summarize:
    label: "📝 总结提炼"
    prompt_append: |
      ## 文档总结模式
      对提供的文档/长文本：
      1. 一句话概括核心内容
      2. 关键要点（3-5 条）
      3. 重要数字/日期/人名提取
      4. 待办事项/行动项（如果有）
      输出尽可能结构化，方便直接使用。

  compare:
    label: "⚖ 对比分析"
    prompt_append: |
      ## 对比分析模式
      对用户提供的多段内容进行对比：
      1. 相同点
      2. 不同点（表格形式）
      3. 各自的优劣
      4. 推荐选择及理由

  debug:
    label: "🐛 调试分析"
    prompt_append: |
      ## 错误调试模式
      对提供的错误日志/堆栈跟踪：
      1. 直接原因（哪一行、什么操作导致）
      2. 根本原因（为什么发生）
      3. 修复方案（按优先级排序）
      4. 预防措施（如何避免再次发生）
      不要猜测 — 如果信息不足，明确指出需要什么额外信息。

  free:
    label: "💬 自由对话"
    prompt_append: ""
    # 不叠加额外提示词，仅用基础分析提示词
```

### 4.3 智能模式推荐

当用户粘贴内容时，分析窗格可以自动检测内容类型并推荐分析模式：

```javascript
// 内容特征检测（纯前端，不需要调 AI）
function detectContentType(text) {
  // 代码特征
  if (text.match(/function|class |def |import |const |let |var |<script|<\/script>|<?php/)) {
    if (text.match(/password|secret|token|api.?key|SQL|SELECT|INSERT|eval\(/i))
      return ['code-review', 'security-audit']
    return ['code-review', 'explain']
  }
  // 错误日志
  if (text.match(/Error|Exception|Traceback|at .+:\d+:\d+|Stack trace|panic|fatal/i))
    return ['debug']
  // 越南语
  if (text.match(/[àáảãạăằắẳẵặâầấẩẫậđèéẻẽẹêềếểễệìíỉĩịòóỏõọôồốổỗộơờớởỡợùúủũụưừứửữựỳýỷỹỵ]/))
    return ['translate']
  // 长文本
  if (text.length > 2000)
    return ['summarize']
  // 多段分隔
  if (text.match(/^={3,}|^-{3,}|^\*{3,}/m) || text.includes('VS') || text.includes('vs'))
    return ['compare']

  return ['free', 'explain'] // 默认
}
```

## 五、架构设计重新审视

### 5.1 数据流架构

```
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│  用户操作      │────▶│  Plugin 层    │────▶│  DeepSeek    │
│               │     │              │     │  API (flash) │
│ - 粘贴内容     │     │ - 模式选择    │     │              │
│ - 选择模式     │     │ - 构建 prompt │     │ 流式返回     │
│ - 追问        │     │ - 流式渲染    │     │              │
│               │     │ - 结果缓存    │◀────│              │
└──────────────┘     └──────────────┘     └──────────────┘
                             │
                             ▼
                      ┌──────────────┐
                      │  ctx.storage  │
                      │  (持久化)      │
                      │ - pane 列表   │
                      │ - 最近结果    │
                      │ - 用户偏好    │
                      └──────────────┘
```

### 5.2 关键设计决策

**1. 不经过 Hermes Agent Loop**
- ❌ 不调用 `host.request('agent.chat', ...)` — 这会走完整的 agent loop
- ✅ 直接 `fetch('https://api.deepseek.com/v1/chat/completions', ...)` — 纯推理，无工具

**2. 有限上下文窗口**
- 每个分析窗格只保留最近 3 轮对话（6 条消息）
- 超过 3 轮自动截断，提示 "历史已清除，开始新的分析"
- 目的：**防止上下文膨胀，保持分析聚焦**

**3. 输入作为上下文主体，对话作为补充**
- 不是 "用户发消息 → AI 回消息 → 用户再发 → AI 再回"
- 而是 "用户粘贴一大段内容 → AI 一次性分析 → 用户可能追问细节"

**4. 结果的"可行动性"**
- 每个分析结果下面有操作按钮：复制、发送到主对话、追问
- "发送到主对话" 通过剪贴板 + 通知实现：复制结果 → 通知用户已复制 → 用户 Ctrl+V 到主对话

### 5.3 组件树

```

├── ModeSelector          // 顶部分析模式选择器（chip/tab 风格）
│   ├── 自动推荐模式       // 智能高亮推荐的分析模式
│   └── 所有可选模式       // 平铺显示
```

## 六、与主对话的联动设计

### 6.1 从主对话到分析窗格

```
主对话中选中文本 → Ctrl+C →
切换到分析窗格 → "📋 粘贴并分析" 按钮（自动读取剪贴板）→
自动检测内容类型 → 推荐分析模式 → 一键开始分析
```

### 6.2 从分析窗格到主对话

```
分析窗格得到结果 →
点击 "📤 发送到对话" →
结果复制到剪贴板 + 通知 "分析结果已复制，请粘贴到对话中" →
用户 Ctrl+V 到主对话输入框 →
主对话 Agent 可以基于分析结果继续执行任务
```

**为什么不用自动化粘贴？** 桌面插件在 Electron 沙箱中，跨窗格操作受限。且用户应该**有意识地决定**哪些分析结果值得进入主对话上下文。

## 七、与原计划的差异总结

| 方面 | 原计划 | 新设计 |
|------|--------|--------|
| 定位 | 副聊天窗口 | 分析工作台 |
| 交互模式 | 对话驱动（无限轮） | 模板驱动（粘贴→分析→追问最多 3 轮） |
| 系统提示词 | 一个通用 prompt | 基础层 + 7 种角色模式叠加 |
| 智能检测 | 无 | 自动识别内容类型，推荐分析模式 |
| 上下文管理 | 保留全部历史 | 最多 3 轮，自动截断 |
| 结果可行动性 | 无 | 复制/发送到对话/追问 |
| 与主对话联动 | 手动粘贴 | 剪贴板桥接 + 智能推荐 |
| 状态栏 | 窗格数量 | 窗格数量 + 当前分析模式 |

## 八、实施建议

分两个阶段：

**Phase 1 — MVP（核心分析能力）**
- 单一分析窗格（先不做多窗格标签栏）
- 分析模式选择器
- 输入→分析→流式输出
- 基础追问（保留 3 轮）
- 内容类型自动检测

**Phase 2 — 多窗格 + 联动**
- 多窗格标签栏
- 状态栏指示器
- 剪贴板桥接
- 结果导出到主对话

这样可以**先验证分析窗格的核心价值**（到底好不好用），再投入多窗格管理的复杂度。
