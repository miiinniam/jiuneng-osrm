# 供应商报价数据提取（通用 Skill，不绑定任何特定 Agent 平台）

> 本文档面向任何能读 Markdown、能执行 shell 命令、能读 Excel/Word/PDF 的编码 Agent
> （Claude Code / Hermes / Codex / 人工）。不依赖任何平台专属的 Skill 格式。
>
> **这是流水线的第一阶段（消化/清洗），不做任何反推公式的数学计算。**
> 把 `供应商报价/` 文件夹里格式各异的原始报价文件（Excel、Word、PDF、格式混乱的表格、
> 越南语/中文混排，什么样的都行）读出来，按正算公式 §6 的数据模型统一提取成一份干净、
> 结构化的样本 JSON。提取完之后，**交给第二阶段的
> [`运费反算SKILL.md`](./运费反算SKILL.md) 去跑真正的反推拟合**——那份文档只管
> "拿到干净数据之后怎么反推市场费率"，不再管"怎么从乱七八糟的原始文件里挖数据"，
> 两件事分开，各自更专注。
>
> **🆕 处理非标准格式**：如果原始文件是图片（聊天截图/照片）、PDF 扫描件、或者
> Excel 表格有复杂合并单元格/多层表头导致 openpyxl 读不出来——请使用
> **[`非标报价智能提取SKILL.md`](./非标报价智能提取SKILL.md)**，
> 那是一个 AI 驱动的智能提取方案，用多模态 vision 能力直接读图识别字段。
> 本文档专注于**规整的 Excel 表格和可编程提取的场景**。

## 1. 这个 skill 解决什么问题

供应商报价单/历史运单来源五花八门：Excel 报价费率表、Word 合同附件、PDF 扫描件、
邮件里贴的截图转表格……格式、语言（越南语/中文/英语混排）、数据形态（逐单结算 vs
价目矩阵）都不统一。但正算公式（`OSRM++/backend/app/services/费用计算公式.py` +
`cost_engine.py`）只认一种输入形状：路线（起终点）、货物信息（重量/类型/货值）、
车辆信息（车型/车身类型）、以及各种可选标志位（空车返回/需要装卸/绕开禁限行等）。

**这个 skill 就是负责把"任意形态的原始报价"转换成"正算公式认识的干净数据"这一步**，
输出一份统一格式的 JSON，字段跟 `app/schemas.py` 里的 `QuoteRequest`/`BatchRowInput`
完全对应，这样不管数据最终是要拿去反推费率、还是单纯做报价比对/市场调研，
都能直接复用这份干净数据。

**触发场景**：用户把供应商报价文件（不管什么格式）丢进 `供应商报价/` 文件夹，
说"帮我把这些报价整理一下"/"把这些报价转成能用的数据"/"帮我消化一下这些报价"。

## 2. 前置条件

- 如果供应商文件是 Excel：用 pandas/openpyxl 读（`OSRM++/backend` 的 Python 环境已经
  装了常用依赖，缺 pandas/openpyxl 的话另外装）。
- 如果是 PDF/Word（不是 Excel）：先用项目里已有的 pdf/docx 文档技能把文字/表格内容
  提取出来，再按下面的方法处理，原理是一样的——先拿到文字/表格，再从里面识别字段。
- 如果是纯图片扫描件（没有文字层）：需要能读图的能力（OCR 或者直接让多模态模型读图），
  按同样的方法从识别出的文字里提取字段；如果读不出来，明确告诉用户这份文件没法自动处理，
  不要瞎猜数据硬凑。
- 想校验提取出来的坐标/距离对不对，本地 OSRM 服务（`start.ps1` 启动，默认
  `http://localhost:5001`）和地理编码（`/geocode`，Nominatim）在跑的话可以顺手核对，
  但这不是提取阶段的必需项——提取阶段只管把文档里的信息转成结构化字段，
  实际算距离/时间是下游反算脚本自己做的事。

## 3. 目标格式（提取完要落到这个 JSON）

不管原始文件长什么样，最终都要整理成这样一个数组，存成一个 `.json` 文件
（放在 `供应商报价/` 目录下，命名 `samples_<供应商名或来源文件名>.json`）：

```json
[
  {
    "origin_address": "Thôn Đồng Lạc, Xã Đồng Lạc, Huyện Lạng Giang, Tỉnh Bắc Giang, Việt Nam",
    "dest_address": "Hà Nội, Việt Nam",
    "loading_mode": "full_truck",
    "vehicle_model_id": "high_side_10t",
    "cargo_type": "normal",
    "weight_kg": 5000,
    "volume_m3": null,
    "empty_return": false,
    "need_loading": false,
    "avoid_restricted_zones": false,
    "avoid_construction_zones": false,
    "via_mountain_road": false,
    "cargo_value_vnd": null,
    "toll_rate_vnd_per_km": null,
    "misc_cost_vnd": 0,
    "actual_cost_vnd": 3400000,
    "source_distance_km": null,
    "source_duration_h": null,
    "notes": "Báo Giá Fushida/Duy Anh 2026-07 — BẮC GIANG→HÀ NỘI, 报价单 XE 5T 列，假设满载（报价单本身没给实际重量），报价不含VAT/超限费，按 CK Hữu Nghị 路线基准价（脚注：走 Tân Thanh 口岸要 +500,000）"
  }
]
```

字段说明（跟正向报价表单的字段完全对应，字段名和取值范围以 `app/schemas.py` /
`app/services/vehicle_registry.py` 为准）：

| 字段 | 必填 | 说明 |
|------|------|------|
| `origin`/`destination`（`{lat,lng}`）或 `origin_address`/`dest_address`（文本地址） | 二选一必填 | 文本地址会自动地理编码，越南语/中文地名都可以，但**建议在地名后面带上省市/国家**（比如"Hà Nội, Việt Nam"而不是单独"Hà Nội"），不然容易编码到同名的别的地方 |
| `loading_mode` | 必填 | `full_truck`（整车/专车专线）或 `consolidated`（拼货/多家共用一车），怎么判断见 §4.5 |
| `vehicle_model_id` | `full_truck` 必填，`consolidated` 时忽略 | 具体车型，取值来自 `OSRM++/车辆型号库/车辆型号库.csv` 的 `model_id` 列（不再是旧的 4 档 `vehicle_type`），怎么从报价单的吨位/车型描述映射到具体 model_id，见 §5 |
| `cargo_type` | 选填，默认 `normal` | `presets.py` 里 `CARGO_TYPE_RATES` 已有的键：`normal`/`cold_chain`/`hazardous`/`oversized`/`other`（这个维度未受本次车型改造影响） |
| `weight_kg` | 必填 | 货物重量。没有具体重量的情况按 §5 的优先级假设，并在 notes 里写清楚 |
| `volume_m3` | `consolidated` 必填（用于容量匹配），`full_truck` 选填仅作参考 | 货物体积，报价单/合同里提取不到时留 `null`，并在 notes 里注明"未提供体积" |
| `empty_return` / `need_loading` | 选填，默认 false | 是否空车返回 / 是否需要装卸服务 |
| `avoid_restricted_zones` / `avoid_construction_zones` / `via_mountain_road` | 选填，默认 false | 绕开禁行限行 / 绕开施工封闭 / 途经上坡山区，原始文件里如果明确提到这类情况就标 true |
| `actual_cost_vnd` | 必填 | 这条样本**实际的价格**（供应商报价单里就是报价单价） |
| `source_distance_km` / `source_duration_h` | 选填，非标准字段 | 如果原始文件里**自己写了**距离/时长，记下来仅作为交叉核对参考——下游反算脚本用 OSRM 重新算距离/时间，不会读这两个字段，只是留个痕迹方便人工排查"OSRM 算出来的距离和文件自称的距离差很多"这种异常 |
| `notes` | 选填但**强烈建议填** | 自由文本，写清楚这条数据的来源文件、原始行/列位置、做了哪些假设——这是保证"公式透明可审计"的关键，也是下一阶段反算 skill 判断样本是否可信的重要线索 |

> **格式提醒（踩过的坑）**：经纬度必须是**嵌套对象** `"origin": {"lat": 21.03, "lng": 105.85}`，
> 不能写成扁平的 `"origin_lat": 21.03, "origin_lng": 105.85`（那是批量导入 Excel 那边
> `BatchRowInput` 的字段风格，反算脚本的 `_load_shipments_from_json` 不认，会被当成
> 没提供经纬度，退回去走地址地理编码那条路）。同一个起点/终点要生成很多条样本时
> （比如下面 §4 的报价费率表场景），建议**先把每个不同的地址各自地理编码一次拿到
> 经纬度、缓存下来，再套进所有样本里**，不要让每条样本都重新查一次地址——供应商报价单
> 常见"一个起点发往几十个目的地"，如果不去重会对公共地理编码服务发几十次重复请求，
> 既慢又不礼貌。

## 4. 供应商报价单常见的两种形态

打开 `供应商报价/` 文件夹里的文件之后，大概率会遇到下面两种情况之一
（也可能是变体，靠自己判断，不强求完全匹配）：

**A. 逐单实际结算记录**（一行 = 一次真实发生的运输，本来就有重量和实付价）——
直接按 §3 的字段对应关系整理即可，这种最干净。

**B. 报价费率表 / 价目表**（供应商给的是"某类车去某个地方多少钱"的价目矩阵，
不针对具体某一次运输，也没有重量列）——比如下面这个真实例子：

```
CÔNG TY TNHH DV&TM DUY ANH          <- 报价方公司（隐含起点：地址在信头里）
Kính gửi: ... FUSHIDA VIỆT NAM      <- 收件方公司
              BẢNG BÁO GIÁ           <- "报价表"

STT | NƠI GIAO HÀNG | XE 1.5T | XE 2.5T | XE 3.5T | XE 5T | XE 8T | XE 10T | XE 3 CHÂN
 1  | BẮC GIANG      | 1,600,000 | 1,900,000 | 2,100,000 | 2,400,000 | 2,700,000 | 3,000,000 | 3,800,000
 2  | BẮC NINH       | 1,700,000 | 2,000,000 | 2,200,000 | 2,600,000 | 2,800,000 | 3,200,000 | 4,100,000
 ...（共10个目的地）

Ghi chú: Cước đi cửa khẩu Tân Thanh cộng thêm 500.000 so với đi CK Hữu Nghị
- Đơn giá trên chưa bao gồm thuế GTGT, phí lưu ca, hàng quá khổ quá tải...
```

这种表格是"目的地 × 车型"的矩阵，**一个单元格就是一条样本**（10 个目的地 × 7 档车型
= 最多 70 条样本，比逐单记录量还大，非常适合拿来反算）。处理方法：

1. **起点**：信头里的报价方地址（"Kính gửi"上面那家公司的地址），比如例子里是
   "Thôn Đồng Lạc, Xã Đồng Lạc, Huyện Lạng Giang, Tỉnh Bắc Giang, Việt Nam"。
2. **终点**：矩阵里每一行的地名列（`NƠI GIAO HÀNG` / "交货地点"），后面记得补上
   "Việt Nam"帮地理编码定位到正确国家，比如"Hà Nội, Việt Nam"。
3. **车型**：矩阵的每一列就是一个车型，按 §5 的方法映射成具体的 `vehicle_model_id`；
   这种"每列一个车型去某地的专车价"的矩阵形态，`loading_mode` 按 §4.5 判断通常是
   `full_truck`。
4. **每个单元格**拆成一条独立样本：`actual_cost_vnd` = 单元格数值，
   `origin_address`/`dest_address` 按上面 1/2，`vehicle_model_id` 按上面 3。
5. **表头/信头/落款/公司盖章图片这些都不是数据**，跳过；找到含 "STT"（或其他
   "序号"/"No."之类字样）的那一行当表头，从下一行开始读，读到第一个整行空白/
   全是页脚说明文字的行为止。
6. **页脚的文字说明**（比如"走 Tân Thanh 口岸加收 500,000"、"报价不含增值税/超限费"）
   这些是非结构化的业务规则，**不会自动套用到样本上**，原样写进每条样本的 `notes` 里
   供人工参考即可（如果确定这批报价就是按脚注里说的默认口岸/默认不含税报的，就不用
   额外处理；如果要单独测算"走 Tân Thanh 口岸"的价格，可以额外生成一份
   `misc_cost_vnd: 500000` 的样本）。

## 4.5 `loading_mode` 怎么判断

新版正算公式区分"拼货"（consolidated，多家货物共用一辆车，按占用运力比例分摊费用）和
"整车"（full_truck，专车专线）两套计价逻辑，提取阶段就要判断这批报价数据属于哪一种：

- **按吨位/车型去某目的地的整车价、每格对应"一辆专车去一个地方"**（§4 的形态 B 就是典型例子：
  矩阵每一列是一个具体车型，单元格是"这辆车去这个地方的价格"，不是按货物实际重量/体积算的）
  -> `full_truck`。
- **按重量/体积/CBM 计费、报价单明确写"拼车"/"零担"/"多家货共用一车"/"ghép hàng"字样**
  -> `consolidated`。
- **不确定时默认按 `full_truck` 处理**，并在 `notes` 里注明"loading_mode 判断依据不明确，
  按默认整车处理，需人工复核"——不要瞎猜成 `consolidated`（`consolidated` 需要额外的
  `volume_m3` 字段和车型自动匹配逻辑，判断错了下游拟合会用错公式）。

## 5. 没有具体重量时怎么假设、车型吨位怎么映射

**假设重量的优先级**：
1. 报价单如果直接写了车型对应的吨位（比如"XE 5T"这种列名本身就带吨位），
   **优先直接用这个标注吨位当 `weight_kg`**（5T 就是 5000kg），这比套用映射后的
   `vehicle_model_id` 对应的 `max_load_ton` 更准——车型库里的具体型号毕竟是有限的几档，
   跟报价单里某一档车的实际吨位不一定完全相等（比如报价单写的是 4.8T，车型库里没有
   刚好 4.8T 的型号，只能就近映射到比如 5T 那一档，这时候还是优先用报价单标注的 4.8T
   当假设重量，不要用映射目标型号的 `max_load_ton` 覆盖掉）。
2. 报价单完全没提到具体吨位（比如只写"大车/小车"这种模糊描述），才退而求其次，
   **用映射到的车型 `max_load_ton` 当作假设重量**（车辆型号库.csv 里能查到）。
3. 不管走哪种，都要在 `notes` 里写清楚这个重量是"报价单标注吨位"还是"按车型档位假设满载"，
   不要不声不响地编一个数字。

**吨位/车型描述 -> `vehicle_model_id` 映射**：不再是写死的 4 档，而是要打开
`OSRM++/车辆型号库/车辆型号库.csv` 现查（车辆型号库是正算/反算共用数据，单独成目录，
不在 `公式反算文件/` 里）——这份表用户会持续手工调整（新增/改吨位/改费率），
映射时永远以当次读到的实际内容为准，不要凭记忆套用旧档位。步骤：

1. 先按报价单描述判断车身大类（对应 CSV 的 `category` 列）：厢式货车/面包车 ->
   `small_box`；平板/挂车（无顶棚厢体）-> `flatbed`；高栏/敞篷带栏板 -> `high_side`；
   集装箱柜车 -> `container`；冷藏/冷链车 -> `cold_chain`。报价单没写车身类型、
   只写了吨位时，默认按 `high_side`（最通用的封闭厢体类型）判断。
2. 在判断出的 `category` 里，找 `max_load_ton` **大于等于**目标吨位、且数值最接近的那一行
   （优先选装得下的，不要选小了；如果所有型号都比目标吨位小，选最大的那个并在 notes
   里注明"超出车型库最大吨位，按最大型号近似"）。
3. 目标吨位从哪来：优先用 §5 第一条"报价单标注吨位"，其次退回该 `category` 里默认档位
   的量级估计。
4. 把选中的 `model_id`（CSV 第二列）填进样本，同时在 `notes` 里写清楚"报价单描述XX ->
   映射到车型库 model_id=XX（依据：吨位最接近/仅有的可用型号等）"，方便日后核对。

> 车型库当前起步是 16 行占位数据（5 大类各 2-4 个型号），随着用户在 Excel 里补充更多
> 细分型号，可选的映射目标会越来越多、越来越精确，不需要更新本文档，直接读当次的
> CSV 内容即可。

## 6. 提取完之后：多文件怎么组织、下一步交给谁

- 每个供应商/每个来源文件先各自整理成一份 `供应商报价/samples_<供应商名>.json`，
  方便追溯来源、方便单独核对某家供应商的数据有没有问题。
- 处理完一批文件之后，给用户一份简短总结：处理了哪些文件、每份提取出多少条样本、
  哪些文件处理不了/需要人工确认（比如格式认不出来、字段缺失、地理编码失败的地名等）。
- **这一步到此为止**——提取出来的干净数据不在本 skill 里继续做任何数学计算。
  想反推市场费率，交给 [`运费反算SKILL.md`](./运费反算SKILL.md)（同一个文件夹下）
  继续处理：那份文档负责把多个供应商的样本合并、跑最小二乘拟合、解读结果、
  判断要不要更新 `presets.py`/`config.py` 里的默认费率。

## 7. 一个真实跑过的例子

`供应商报价/samples_DuyAnh_Fushida.json` 就是照着本文档的方法，从
`供应商报价/Báo Giá Fushida  (2026年7月2日).xlsx`（一份越南语的报价费率表，
北江省 Duy Anh 公司发给 Fushida 越南公司的车型/目的地价目矩阵）提取出来的，
63 条样本（10 个目的地 × 7 档车型，减去起点终点同省份、地理编码重合的 1 组目的地）——
矩阵每列对应一辆专车去某目的地的价格，属于典型 `full_truck`（整车）案例。
（`vehicle_type`/`body_type` 迁移到新 `vehicle_model_id` 体系时，按 §5 的方法就近
映射到了 `high_side_5t`/`high_side_10t`/`high_side_18t` 三个具体型号——原报价单的
1.5T/2.5T/3.5T 都落进了 `high_side_5t`，跟旧 4 档体系"多个吨位挤进同一档"是同一类局限，
车型库以后细分更多型号会自然改善。）这份提取结果交给 `运费反算SKILL.md` 处理之后的
拟合结果和踩过的坑，记录在那份文档的"一个真实供应商报价的案例"章节里。
